# Competitive landscape: RL environment and grader QA

**Access date for every source and API observation: 2026-10-26 (Europe/Moscow).** Repository timestamps below retain GitHub's UTC values. Scope: public tools and offerings relevant in 2024–2026; requested older harnesses are included because of their current tooling. This is a source review, not a runtime evaluation or an exhaustive market census.

**Finding:** Hackproof enters an existing market. Benchmark auditing, automatic verifier repair, model-free gold/no-op validation, commercial task QA, and private grader-audit certificates already exist. A defensible direction is an open, reproducible property-checking layer with explicit statistical methods and framework adapters. The difference must be demonstrated at the level of individual checks, rather than claimed for “environment QA” as a category. See R01, R03, R06, R11, R16 and C01–C03 below.

Hackproof's comparison target is the **planned scope in `codex/README.md`**, not an assertion that every proposed check is implemented:

| Property | Intended assertion |
|---|---|
| P1 | Do-nothing / empty-answer baselines earn zero reward. |
| P2 | Agent-modifiable state cannot alter the authoritative grader. |
| P3 | The actual agent sandbox contains no answer, test or reference-solution copy. |
| P4 | The grader rejects near-miss mutations of the reference solution. |
| P5 | The reference passes repeatedly; flake uncertainty is reported with Wilson intervals. |
| P6 | Judge scores remain stable under content-neutral transformations. |
| P7 | Task difficulty is calibrated with Beta posteriors and SPRT. |

**Reading the tables:** “Partial” means a related test or defense, not the full property above. “Support” means infrastructure authors can use to implement a check. Missing features mean **not established in the reviewed sources**, not proven absent from an entire codebase or private product. Provider claims and empirical results were not independently reproduced. API license values describe the repository, not necessarily every included dataset or dependency. `UNVERIFIED` license means GitHub returned no detected license; no reuse permission is inferred.

### Details that change positioning

- **Verifiers is a direct validation competitor.** Its implementation is more informative than its short README: setup/gold/no-op checks are model-free, with explicit invalid/unchecked/error/timeout outcomes. Hackproof can add value through stricter baseline semantics and additional properties, but cannot claim to introduce model-free validation. [^R03]
- **Harbor already checks leakage at review time.** Its default rubric explicitly asks about tests/solutions copied into images and future repository information. The current nested `task check` command is a removed-command migration stub pointing to `harbor check`; older documentation still advertises the nested form. These are source observations, not a CLI smoke test. [^R06]
- **OpenEnv already collects runtime evidence.** Network-policy grading uses measured reachability and returns `SKIP` for unsupported modes or unavailable evidence. Hackproof should integrate useful upstream checks and add semantic/grader-specific assertions. [^R08]
- **Terminal Wrench has both data and a separate hardening implementation.** Treating the dataset alone as the entire offering would miss `few-sh/harden-v0`. The paper's release count and the dataset README's count are version-specific; this survey does not combine them or estimate current task vulnerability prevalence. [^R02] [^R11]

## Where Hackproof is different

These are **proposed, testable differences from the reviewed evidence**, not globally unique inventions or shipped-feature claims. The comparison target is the seven-property scope above.

1. **Zero-reward negative controls with explicit reward semantics.** Verifiers' untouched-task criterion permits partial reward below 1.0. Hackproof specifies zero for trivial baselines, and could document normalization and legitimate exceptions. This is a precise potential difference; whether it improves a particular task requires evidence. [^R03]
2. **Reference mutation as a repeatable grader regression suite.** BenchJack audits architecture; `harden-v0` searches and repairs; UTBoost augments tests. Hackproof can supply fixed mutation operators, positive controls and per-mutant outcomes after each grader change. Equivalent systematic reference-mutation coverage was not established in these reviewed sources. [^R01] [^R11] [^R12]
3. **Statistical reference reliability rather than a single gold pass.** Verifiers and SWE-bench already offer reference validation; Proofbench advertises same-process repeatability. Hackproof's proposed Wilson intervals distinguish observed clean runs from a bound on failure probability. Exact sampling conditions, fresh execution and cache handling must be part of the evidence. [^R03] [^R09] [^R16]
4. **A specified judge-invariance test and difficulty stopping rule.** CHERRL studies judge bias, while CATCH and Proximal study difficulty-related behavior. The reviewed evidence did not establish a packaged combination of neutral judge transformations with Beta posterior difficulty estimates and SPRT. This is an evidence gap worth validating, not proof that no competitor implements it. [^R14] [^R15] [^C03]
5. **Open execution and reusable adapters.** A published check implementation, frozen input identity and reproducible reruns could differentiate Hackproof from Proofbench's private engine and hosted QA offerings. Open-source status alone does not distinguish it from BenchJack, Verifiers, Harbor or OpenEnv; adapters should extend those ecosystems. [^R01] [^R03] [^R06] [^R08] [^R16] [^C01]

## Threats

The following are strategic inferences from current public capabilities, **not announcements or predictions with verified deadlines**:

| Actor | Why it could expand into the same scope | Implication |
|---|---|---|
| Prime Intellect / Verifiers | Already owns task definitions, runtimes, isolated-scoring configuration, gold and no-op validation. [^R03] | Highest integration threat: another CLI validation mode could absorb individual checks. Build an adapter and offer methods/reporting worth retaining. |
| Harbor maintainers | Already distributes task QA, rubric review and the execution harness. [^R06] | Task-author workflow is already occupied; show concrete checks that review-based QA does not measure. |
| BenchJack and `harden-v0` teams | Already inspect grader weaknesses or run discovery/repair/legitimate-solver loops. [^R01] [^R11] | Automated replay and statistical validation are plausible extensions. Compete on reproducibility and regression cost, not discovery of reward hacking. |
| HUD and Applied Compute | Advertise task QA or reward-hacking monitoring inside platforms used to run tasks. [^C01] [^C02] | QA can be bundled with hosting/training; an independent tool needs portability and inspectable evidence. |
| Proofbench | Already pitches cheap structural checks, zero-reward probes and bounded audit certificates. [^R16] | Very close positioning despite tiny public footprint. Open engine and independently executable evidence matter more than a generic certification label. |
| OpenEnv and Proximal | Respectively maintain evidence-based environment validation and conduct rollout-based quality/difficulty research. [^R08] [^C03] | Could broaden existing validation or internal QA. Integrate contract checks and keep semantic acceptance claims precise. |

## Search coverage, exclusions and unresolved questions

Read all ten requested seed READMEs and the additional repositories listed below. Inspected selected implementations where short READMEs hid important features. Used read-only GitHub metadata, README/Contents and tree APIs; no repository was cloned, installed or run. No paid API or model call was made, and no account sign-in or outward write occurred.

GitHub repository searches used the exact phrases `"reward hacking detection"`, `"benchmark validity"`, `"environment QA"`, `"verifier audit"`, and `"grader robustness"`, with up to five returned candidates per query under GitHub's default ranking. These searches are noisy: infrastructure staging, generic verification and unrelated model-evaluation projects appear. They are discovery evidence only, not support for completeness. Proofbench and Benchmark Caliper were identified this way. Web discovery additionally found RewardScope, CHERRL, CATCH, UTBoost and Applied Compute. [^Q]

**Excluded adjacent tool:** Benchmark Caliper assesses cultural/deployment-context validity using paper and item analysis. Its current README does not describe runtime grader-isolation or reward-function auditing. “Bayesian auditing” in that repository is not evidence of Hackproof's P7 task calibration. Public code exists, but an OSS license was not verified. Metadata: 1 star, created 2026-02-13, last push 2026-10-25. [^R17]

Unresolved: exact sensitivity/false-alarm rates on shared defensive fixtures; licensing of individual redistributed artifacts; hosted QA availability and pricing; Proofbench customer use and exact dirty engine state; cross-process reference reliability; treatment of valid alternative solutions. A passing mutation suite cannot by itself establish that a grader fairly accepts every valid solution. Runtime capability and comparative performance remain **UNVERIFIED** because the task prohibits running third-party tools.
